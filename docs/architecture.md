# Архитектура первой версии Cloudya

Статус: согласованное проектное решение для задач 1–9 из `AGENTS.md`. Этот документ описывает контракт между модулями; реализация ещё не завершена. Байтовый формат и сообщения описаны в [protocol.md](protocol.md).

## Объём

Два профиля приложения в одной локальной IPv4-сети синхронизируют одну общую папку в обе стороны. Каждый профиль хранит собственную рабочую копию. В первой версии синхронизируются создание и изменение файлов; локальное удаление не передаётся как удаление. При независимых правках сохраняются обе версии и показывается конфликт. Облачный сервер, учётные записи, синхронизация более двух узлов и докачка частей файла не входят в первую версию.

Оба профиля слушают TCP и могут инициировать соединение. Начальный путь пользователя: ручной адрес → сопряжение устройств → защищённое приглашение к папке → двусторонняя синхронизация. UDP-поиск и автоматическое подключение добавляются после работающего ручного сценария. Обнаружение сообщает адрес, но не даёт доверия или доступа.

## Профиль и расположение данных

При первом запуске профиля создаются случайный UUIDv4 `device_id`, закрытый ключ и самоподписанный сертификат X.509. Они сохраняются между запусками. Для тестов два процесса запускаются с разными каталогами профиля, БД, ключами, локальными корнями и TCP-портами. IP, порт и отображаемое имя могут меняться без смены `device_id`.

Корень профиля получают через `QStandardPaths::AppLocalDataLocation`; у тестового профиля он может задаваться параметром запуска. Точный путь определяет ОС, а не синхронизируемая папка. Предлагаемая структура:

```text
<profile>/
  identity/
    device.key.pem       закрытый ключ своего устройства
    device.crt.pem       открытый сертификат своего устройства
  peers/
    <device_id>.crt.pem  открытый сертификат доверенного устройства
  index.sqlite           устройства, отпечатки, доступы, папки и версии
```

Закрытый ключ хранится в PEM только на своём устройстве, с доступом для владельца учётной записи; приложение не экспортирует его в действии «Поделиться сертификатом». На Windows требуются ограничения доступа ОС для текущего пользователя, на Linux — права владельца на каталог и файл. Файлы профиля не входят в синхронизируемый корень, репозиторий и обычный экспорт данных. Шифрование ключа паролем, который лежит рядом с ним, не добавило бы защиты; аппаратное или системное хранилище ключей можно рассмотреть отдельно. При ошибке чтения существующей идентичности приложение сообщает об ошибке и не генерирует её молча заново.

Для совместимости Linux и Windows выбираем ключ RSA 3072 бит и сертификат, подписанный SHA-256. Сертификат содержит `device_id` в SAN URI вида `urn:cloudya:device:<uuid>`, назначения `clientAuth` и `serverAuth` и `basicConstraints CA:FALSE`. Срок действия — 5 лет; перед истечением приложение предупреждает пользователя, замена сертификата требует повторного сопряжения. Генерация выполняется программно при первом запуске через криптографическую библиотеку; установленная у пользователя командная утилита `openssl` не требуется. Детали вызовов OpenSSL относятся к задаче 5.

## Сопряжение и доверие

Публичный сертификат можно экспортировать в `.pem`, перенести на второе устройство и импортировать там. Пользователь сверяет показанный приложением отпечаток SHA-256 сертификата с отпечатком на исходном устройстве. Для взаимного TLS оба устройства должны получить и подтвердить сертификат другого. Экспортируется только сертификат, никогда закрытый ключ.

Пользовательский сценарий первой версии: на A выбрать папку и открыть экран «Поделиться» с локальным `IP:порт` и отпечатком; на B выбрать «Добавить устройство», указать адрес A и импортировать сертификат A; затем выполнить обратный импорт сертификата B на A и сверить оба отпечатка. После защищённого подключения A отправляет приглашение, а B выбирает пустой локальный каталог. При следующем запуске сертификаты и привязка папки уже сохранены. Поиск через UDP позже заменит ручной ввод адреса списком найденных устройств, но не шаг проверки доверия.

Запись доверия связывает `device_id` с точным сертификатом (или его SHA-256 по DER-кодировке), а не с IP-адресом, именем либо просто заявленным `device_id`. При TLS обе стороны предъявляют сертификаты и доказывают владение закрытыми ключами. Приложение принимает лишь заранее подтверждённый сертификат, проверяет срок действия и привязку к `device_id`. Самоподписанность обрабатывается только для явно сохранённого сертификата; отключать проверку всех TLS-ошибок для рабочего режима нельзя. Несовпадение, отсутствие сертификата или новый сертификат старого `device_id` прекращают сессию до выдачи индекса. Требуется явное повторное сопряжение после замены ключа или сертификата.

Доверие к устройству и доступ к папке — разные решения. Владелец папки создаёт `folder_id` и приглашает доверенное устройство. Второй пользователь явно принимает приглашение и выбирает пустую локальную папку. Затем оба сохраняют привязку общего `folder_id` к своему локальному пути. До подтверждения доступа узел не раскрывает индекс и содержимое папки. Отзыв доверия закрывает будущие подключения; отзыв доступа к папке закрывает только эту папку.

## Общие типы и инварианты

Ниже — логические типы контракта. Они не задают способ хранения C++-объектов или точные имена классов.

| Тип | Поля | Правило |
|---|---|---|
| `DeviceIdentity` | `device_id: UUID`, `name: string`, `cert_sha256: 32 bytes` | ID постоянен; имя меняется; отпечаток привязан к ID. |
| `PeerEndpoint` | `device_id: UUID`, `address: IPv4`, `port: uint16` | Адрес и порт — только способ подключения, не идентичность. |
| `SharedFolder` | `folder_id: UUID`, `owner_device_id: UUID` | ID создаёт предлагающая сторона; один и тот же ID используется на обоих узлах. |
| `LocalFolderBinding` | `folder_id: UUID`, `local_root: absolute path`, `allowed_peer_ids: set<UUID>` | Локальный корень никогда не передаётся как сетевой путь. |
| `FileVersion` | `version_id: UUID`, `folder_id: UUID`, `relative_path: UTF-8 string`, `size: uint64`, `sha256: 32 bytes`, `vector: map<device_id,uint64>`, `availability` | ID создаётся при локальной правке и сохраняется при передаче; у одного пути может быть несколько версий. |
| `SyncStatus` | `phase`, `folder_id?`, `relative_path?`, `bytes_done?`, `bytes_total?`, `error?` | `phase`: `idle`, `connecting`, `pairing`, `syncing`, `conflict`, `error`, `complete`. UI получает события, а не читает сетевые кадры. |

Относительный путь в протоколе использует `/`, не содержит абсолютного корня, `..`, пустых сегментов и служебного каталога приложения. Перед чтением и записью проверяются симлинки, Windows reparse points, несовместимые имена и коллизии регистра. Для каждой несовместимости выдаётся ошибка конкретного пути.

Вектор версии хранит счётчики по `device_id`. Локальная правка увеличивает локальный счётчик. Принятая версия сохраняет исходный вектор. Версия причинно новее другой, когда каждый её компонент не меньше, а хотя бы один больше. Несравнимые векторы при разных SHA-256 дают конфликт. При одинаковом содержимом векторы можно объединить покомпонентным максимумом без повторной передачи; исходные `version_id` сохраняются как известные идентификаторы, чтобы повторный обмен не создавал дубликаты. Для разных содержимых обе версии остаются в метаданных исходного пути, а дополнительная копия лежит в служебном каталоге, исключённом из сканирования. Правило выбора версии для основного имени должно быть одинаковым на обоих узлах: меньший `version_id` в лексикографическом порядке UUID. Действие «Оставить эту версию» создаёт новую версию с максимумом конфликтующих векторов и увеличенным локальным счётчиком.

Полученный файл сначала пишется во временное хранилище. После проверки размера и SHA-256 он публикуется атомарно, затем подтверждается в индексе. Незавершённое применение и подтверждённая версия хранятся отдельно. После перезапуска незавершённое применение сверяется с диском. Сканирование не считает принятую версию новой локальной правкой, если содержимое совпадает. Исчезновение файла локально не распространяется как удаление; имя, появившееся после переименования, считается новым путём.

Закрытый ключ и сертификат нужны для защиты соединения и идентификации устройства. Они не шифруют файлы на диске. SHA-256 файла в индексе служит проверке содержимого и не заменяет сертификат или проверку доступа к папке.

## Границы модулей

Сохраняем существующее окно и CMake, добавляем каталоги по подсистемам внутри `src/`:

```text
src/
  core/       общие типы, векторы версий, правила относительных путей
  network/    TCP/TLS, кадры, обнаружение UDP
  storage/    сканирование, SQLite, безопасная публикация файлов
  sync/       состояние обмена, сравнение индексов, конфликты
  ui/         существующее окно, действия пользователя и отображение статусов
  main.cpp    создание профиля и связывание модулей
```

`network` передаёт типизированные сообщения и не читает рабочую папку. `storage` не знает о виджетах или сокетах. `sync` связывает транспорт и индекс. UI отправляет команды и получает статусы; долгие сканирование и передача не выполняются в потоке интерфейса. На первом этапе достаточно общих заголовков и компилируемых стабов; отдельные CMake-библиотеки можно выделить при реализации, если это упростит зависимости.

Компилируемые контракты первой задачи находятся в `src/core/types.h` и `src/network/frame.h`. Имена полей C++ используют `camelCase`, имена JSON — `snake_case`; преобразование находится на границе `network`/`sync`. `FrameDecoder::feed()` принимает произвольный кусок TCP-потока и возвращает ноль или несколько кадров либо ошибку. После ошибки декодер нельзя продолжать без `reset()` и новой сессии. `encodeFrame()` возвращает пустой `optional` при недопустимом типе или превышении лимита. Фрейм не проверяет JSON, TLS, права на папку или путь — эти проверки выполняет синхронизатор перед побочными эффектами.

Соглашение между исполнителями по вызовам:

| Модуль | Предоставляет | Вызывает / получает |
|---|---|---|
| `network` | `listen(port)`, `connect(address, port)`, `send(Frame)`, событие `frameReceived(peer, Frame)`, событие `disconnected(peer, reason)` | Проверку TLS-идентичности перед выдачей `peer`; кадры не содержат локальных путей. |
| `storage` | `scan(folderId)`, `indexPage(folderId, cursor, limit)`, `readVersion(versionId)`, `beginReceive`, `appendChunk`, `commitReceive`, `recoverPending` | Абсолютный локальный корень из сохранённой привязки; операции выполняются вне потока UI. |
| `sync` | `invite(folderId, peer)`, `start(folderId, peer)`, `resolveConflict(path, versionId)`, события `SyncStatus` | Транспорт, индекс и проверку доступа; одна активная сессия на пару устройств. |
| `ui` | Ввод адреса, выбор корня, экспорт/импорт сертификата, действия подключения и синхронизации | Только команды `sync` и события статуса; не разбирает JSON или SQLite. |

Это контракт поведения, не требование точно таких методов в C++: асинхронные операции используют Qt signals/slots или callbacks, а конкретные сигнатуры и владение объектами фиксируются при реализации соответствующего модуля. Сообщение о завершении операции всегда содержит `folder_id` и код ошибки либо успешный результат; UI не должен определять результат по исчезновению индикатора.

## Локальный индекс и восстановление

SQLite — источник подтверждённых метаданных, а содержимое файла остаётся на диске. Минимальная схема для реализации задачи 3 и последующих задач:

| Таблица | Ключи и содержимое |
|---|---|
| `profile` | Один `device_id`, имя, отпечаток собственного сертификата, версия схемы. |
| `peers` | `device_id` PK, отпечаток доверенного сертификата, имя, последний адрес и порт, состояние доверия. |
| `folders` | `folder_id` PK, владелец, абсолютный локальный корень, имя. |
| `folder_access` | `(folder_id, device_id)` PK, право на чтение и запись, состояние приглашения. |
| `versions` | `version_id` PK, `folder_id`, относительный путь, размер, SHA-256, расположение содержимого, доступность, время/размер для ускорения сканирования. Индекс по `(folder_id, relative_path)`. |
| `version_counters` | `(version_id, device_id)` PK, счётчик вектора версии. |
| `version_aliases` | `alias_version_id` PK → канонический `version_id` при объединении версий с одинаковым содержимым. |
| `pending_writes` | `transfer_id` PK, версия, временный путь, целевой путь, ожидаемый хеш/размер и стадия применения. |

Уникальность пути в `versions` не устанавливается: конфликт хранит несколько версий под одним путём. Уникальным остаётся `version_id`. Для Windows дополнительно проверяется коллизия путей без учёта регистра до записи. Версии недоступных локально файлов остаются в БД и передаются в сетевом индексе с `available: false`, чтобы другой узел видел расхождение, но не запрашивал недоступное содержимое. Неизвестная версия с уже существующим `version_id` и иным хешем — ошибка, а не замена записи. Полный алгоритм сравнения двух индексов описан в [synchronization.md](synchronization.md).

Получатель до публикации создаёт запись `pending_writes` транзакцией, пишет во временный файл в том же файловом томе, сверяет размер и SHA-256, затем атомарно заменяет цель. Следующей транзакцией фиксирует версию, вектор и удаляет `pending_writes`. После сбоя до второй транзакции `recoverPending` сверяет хеш цели и временного файла: завершает запись, повторяет применение или удаляет повреждённый временный файл. Ни один из этих шагов не объявляет файл сохранённым партнёру до подтверждения БД. После перезапуска сканер сравнивает хеш с подтверждённой версией, чтобы не увеличить локальный счётчик за принятый файл.

Служебный каталог конфликтов и временных приёмов создаётся внутри локального корня под зарезервированным именем `.cloudya` и исключается из сканирования. Пользовательский файл с таким именем отклоняется как `INVALID_PATH`. Перед записью проверяются каждый компонент пути и фактический родительский каталог; симлинки и Windows reparse points не проходятся. Если платформа не может безопасно создать или заменить путь, файл остаётся ошибкой конкретного пути, остальные продолжают обмен.

## Порядок проверки

1. Два профиля на одном компьютере: ручное подключение, взаимное доверие, приглашение, передача файла, совпадение SHA-256.
2. Linux и Windows в одной LAN: файл в обе стороны; смена IP не требует повторного доверия.
3. Независимые офлайн-правки: обе версии доступны, выбор итоговой версии сходится на обоих узлах.
4. UDP-обнаружение: известное устройство появляется с новым IP; ручной адрес работает при отключённом UDP.

Первая задача завершена, когда типы и сетевой контракт зафиксированы, по ним можно написать стабы задач 2–4, а сборки Linux и Windows проходят. Этот документ сам по себе не означает, что остальные задачи реализованы.

## Справка по API

- [Qt QSslSocket](https://doc.qt.io/qt-6/qsslsocket.html) — предъявление сертификата и закрытого ключа, проверка партнёра.
- [Qt QSslCertificate](https://doc.qt.io/qt-6/qsslcertificate.html) — PEM/DER и SHA-256 отпечаток через `digest()` с явно выбранным алгоритмом.
- [Qt QStandardPaths](https://doc.qt.io/qt-6/qstandardpaths.html) — каталог данных приложения.
- [OpenSSL `req`](https://docs.openssl.org/master/man1/openssl-req/) — формат и создание самоподписанного сертификата; в приложении генерация выполняется программно.
