# Синхронизация при расхождении индексов

Статус: проектный контракт для задач 3, 6 и 7. Применяется к одной общей папке и двум доверенным устройствам. Сетевые сообщения и кодирование определены в [protocol.md](protocol.md); локальные версии и правила записи — в [architecture.md](architecture.md).

## Принцип

**При каждом подключении оба узла обмениваются полными индексами папки.** Сохранённый номер прошлой синхронизации не нужен для определения изменений. Повторная синхронизация без правок передаёт метаданные, но не содержимое файлов. Отправляются все подтверждённые активные версии каждого пути: версии, не вытесненные причинно более новой версией, включая версии с временно недоступным содержимым. Если одинаковое содержимое известно под несколькими `version_id`, в индекс включается запись для каждого известного ID с общим объединённым вектором. Старые вытесненные версии могут оставаться в локальной БД, но не предлагаются как активные.

Отсутствие пути в индексе не является командой удалить его у соседа. `available: false` сохраняет знание о версии, которую нельзя сейчас передать. Состояние `pending_writes` никогда не объявляется подтверждённой версией.

## Один цикл обмена

1. После TLS и `Hello` стороны согласуют `folder_id` через `FolderInvite`/`FolderAccept` или `SyncStart`. Обе проверяют доверие и право доступа к этой папке **до** раскрытия индекса.
2. Каждая сторона сканирует свой локальный корень и завершает запись новых локальных версий в SQLite. После сканирования она создаёт неизменный снимок подтверждённых метаданных с новым `snapshot_id` UUIDv4. Снимок материализуется локально или читается из согласованного состояния БД; изменять его страницы во время отправки нельзя. Долгую сетевую передачу нельзя удерживать в открытой транзакции записи SQLite.
3. Оба узла отправляют записи снимка по порядку `(UTF-8 bytes(relative_path), version_id)` в `IndexPage` с `page_number` от 0, затем `IndexEnd`. Каждая страница содержит тот же `snapshot_id`. Получатель проверяет порядок, номер и `page_count`; недопустимый снимок закрывает обмен без применения его решений.
4. После обоих `IndexEnd` каждый узел сравнивает локальный и удалённый наборы по `relative_path`. Для большого индекса страницы хранятся во временном локальном хранилище или сравниваются потоково; весь индекс не обязан находиться в памяти.
5. Узел формирует `FileRequest` только для нужной ему версии с `available: true` у партнёра. Запросы сортируются по пути и ID. Для одной папки ограничивается число одновременно принимаемых файлов; первая реализация использует одну передачу за раз в каждом направлении.
6. Перед `FileBegin` источник повторно открывает файл и проверяет, что байты соответствуют заявленным размеру и SHA-256. Если файл изменился, он сообщает `CONTENT_UNAVAILABLE` для этого запроса и включит новую версию в следующий цикл. Получатель сверяет данные перед публикацией, затем отправляет `FileStored`.
7. После всех доступных передач стороны отправляют `SyncComplete`. `outcome: complete` допустим только если все решения для этого снимка применены или уже присутствуют и не осталось недоступных активных версий или ошибок пути. Иначе передаётся `partial` с числом проблемных путей; UI показывает причины и позволяет повторить обмен.

Снимок означает состояние *на момент сканирования*, а не блокировку пользовательской папки. Правка после этого момента попадёт в следующий цикл. Если целевой путь изменился после сканирования или во время приёма, получатель сканирует его заново перед публикацией и применяет ту же таблицу решений. Новая локальная правка не перезаписывается молча.

## Сравнение версий одного пути

Для векторов `V1` и `V2` отсутствующий компонент считается нулём. `V1` доминирует `V2`, если каждый компонент `V1 >= V2` и хотя бы один строго больше. Сравниваются подтверждённые активные версии **одного и того же** `folder_id` и `relative_path`.

| Локальное и удалённое состояние | Решение |
|---|---|
| Путь или версия есть только у одного узла и содержимое доступно | Другой узел запрашивает версию. Никакого удаления по отсутствию записи нет. |
| Одинаковый `version_id`, одинаковый SHA-256 и вектор | Считать версию общей; файл повторно не передавать. При `available: false` у одной стороны и `true` у другой недоступная сторона может запросить восстановление. |
| Одинаковый `version_id` и SHA-256, но разные векторы | Объединить векторы покомпонентным максимумом; содержимое не передавать, если оно уже доступно локально. |
| Одинаковый `version_id`, разный SHA-256 | Ошибка целостности `VERSION_MISMATCH`; не перезаписывать содержимое и не объявлять успех. |
| Разные ID, одинаковый SHA-256 | Объединить векторы покомпонентным максимумом; оба ID сохранить как известные для того же содержимого. Если байты уже доступны локально, передачи файла нет. Когда байты доступны только на одной стороне, другая запрашивает одну копию. |
| Разный SHA-256, удалённый вектор доминирует локальный | Запросить удалённую версию, проверить и сделать её основной. Старую вытесненную версию можно оставить локально как историю; она не является конфликтом. |
| Разный SHA-256, локальный вектор доминирует удалённый | Удалённый узел запрашивает локальную версию; локальная сторона не меняет файл. |
| Разный SHA-256, векторы несравнимы | Обе версии сохраняются как конфликт. Сторона, которой не хватает байтов версии, запрашивает её. Основное имя получает версия с меньшим `version_id`; вторая копия хранится в `.cloudya` и доступна в UI. |
| Равные векторы, но разный SHA-256 или разные ID с разным SHA-256 | Ошибка `VERSION_MISMATCH`: при корректном учёте правок такое состояние неоднозначно. Нельзя выбирать по времени или ID. |
| Нужная версия есть только с `available: false` на обоих узлах | Передачи нет; сохранить метаданные и показать `partial`/`CONTENT_UNAVAILABLE`. |

Если у одного пути больше двух активных версий, правило сравнения применяется ко всем парам; ни одна несравнимая версия не теряется. Векторная версия и SHA-256 важнее времени изменения. `mtime` и размер помогают решить, требуется ли повторное хеширование при сканировании, но время не определяет победителя конфликта.

При одинаковом хеше оба узла, получив полные индексы, вычисляют один и тот же максимум векторов и обновляют локальные метаданные. Поэтому отдельное сетевое сообщение о слиянии не требуется. Известные `version_id` не удаляются из метаданных: следующий полный индекс позволит распознать уже полученное содержимое. Изменение вектора при том же ID и хеше допустимо только как результат такого слияния; меньший вектор не должен заменить больший.

## Сбой, повтор и гарантии

- Обрыв соединения завершает текущий цикл. При следующем подключении создаются новые снимки и снова выполняется полный обмен; подтверждённые версии распознаются по ID и SHA-256, поэтому новые копии не появляются.
- `FileStored` означает, что содержимое проверено и метаданные зафиксированы. При обрыве до подтверждения отправитель не делает вывод об успехе. Получатель после перезапуска сверяет `pending_writes` с диском; затем новый индекс отражает результат восстановления.
- Если источник перестал иметь байты объявленной версии, он отвечает `CONTENT_UNAVAILABLE`, а получатель сохраняет прежнюю целую копию. Изменившийся файл появится в следующем снимке.
- Если путь исчез локально, это не удаление. Доступная версия второго узла может восстановить его. Если локально известна более новая, но недоступная версия, старое содержимое не объявляется окончательным состоянием: цикл остаётся `partial` до восстановления или решения пользователя.
- Если обе стороны одновременно инициируют синхронизацию, используется одна TCP-сессия на пару устройств; повторный `SyncStart` этой же папки не создаёт второй цикл. Передача по одному пути сериализована.

## Проверяемые сценарии

1. A имеет файл, B пуст: B получает файл; второй обмен не посылает `FileChunk`.
2. B редактирует полученный файл: A получает новую версию; оба имеют одинаковый хеш и вектор.
3. A и B независимо редактируют файл офлайн: после обмена оба имеют две версии и один и тот же выбор основного имени; повтор не создаёт копий.
4. Одинаковое содержимое появилось независимо: векторы объединяются без передачи уже имеющихся байтов.
5. Обрыв посередине файла, перезапуск и новый обмен: прежняя целая версия остаётся доступной до `FileStored`; частичная передача начинается заново.
6. Файл пропал на одном узле: его можно восстановить с другого; исчезновение не удаляет файл у соседа.
7. Файл изменился между `IndexPage` и `FileBegin`: источник сообщает об ошибке конкретного запроса, затем новый цикл обнаруживает новую версию.
8. Страница с чужим `snapshot_id`, пропущенным номером или неверным `page_count` отклоняется; частичный индекс не приводит к записи файлов.
