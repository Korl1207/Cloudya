# Сетевой протокол первой версии

Статус: контракт для реализации. См. также [architecture.md](architecture.md). Протокол работает поверх взаимного TLS по TCP. Ни одно сообщение о папке или файле не обрабатывается до проверки доверенного сертификата и успешного `Hello`.

## Кадр

Все целые числа в сетевом заголовке и бинарной нагрузке передаются в big-endian. Версия протокола для этой спецификации — `1`.

```text
offset  size  поле
0       4     length: uint32 — число байт после поля length
4       2     type: uint16
6       N     payload: length - 2 байта
```

Допустимо `2 <= length <= 131 072` (128 КиБ после поля `length`; полный кадр — максимум 131 076 байт). Неизвестный тип, неверная длина или превышение лимита закрывают сессию с локальной диагностикой. Чтение из TCP не соответствует границе кадра: декодер накапливает неполный кадр и извлекает несколько кадров из одного чтения. Лимит входного буфера — 2 МиБ, исходящей очереди — 8 МиБ; при заполнении очереди производитель ждёт освобождения места, а не бесконечно добавляет данные. Одно чтение ограничено 4096 кадрами; при нарушении сессия закрывается и кадры этого чтения не обрабатываются. Для одной пары устройств допускается одна активная сессия синхронизации.

Если не сказано иначе, `payload` — объект JSON в UTF-8; обязательные поля проверяются строго, неизвестные дополнительные поля версии 1 можно игнорировать. JSON-метаданные ограничены 64 КиБ на кадр. UUID передаётся строкой в каноническом формате; SHA-256 — 64 шестнадцатеричных символа в нижнем регистре. Значения `uint64` в JSON (`size`, счётчики вектора, значения прогресса) передаются десятичными строками без знака: JSON-число может потерять точность. Большие индексы делятся на страницы. Содержимое файла передаётся только бинарными `FileChunk`.

## Типы сообщений

| Код | Сообщение | Обязательные поля / назначение |
|---:|---|---|
| 1 | `Hello` | `protocol_version`, `device_id`; первое сообщение каждой стороны после TLS. ID должен совпасть с доверенной записью сертификата. |
| 2 | `HelloAck` | `protocol_version`; подтверждение совместимости. |
| 3 | `FolderInvite` | `folder_id`, `owner_device_id`, `display_name`; предложение папки доверенному устройству. |
| 4 | `FolderAccept` | `folder_id`; подтверждение пользователя после выбора локального корня. Путь остаётся локальным. |
| 5 | `FolderReject` | `folder_id`, `reason`; отказ от приглашения. |
| 6 | `IndexPage` | `folder_id`, `page_number`, `entries`; ограниченная страница версий файлов. Записи содержат путь, `version_id`, размер, SHA-256 и вектор. |
| 7 | `IndexEnd` | `folder_id`, `page_count`; конец текущего снимка индекса. |
| 8 | `FileRequest` | `folder_id`, `relative_path`, `version_id`; запрос конкретной доступной версии. |
| 9 | `FileBegin` | `transfer_id`, `folder_id`, `relative_path`, `version_id`, `size`, `sha256`, `vector`; начало передачи. |
| 10 | `FileChunk` | Бинарная нагрузка: `transfer_id` (16 байт UUID), `offset` (uint64), затем до 65 536 байт содержимого. |
| 11 | `FileEnd` | `transfer_id`; отправитель закончил поток. |
| 12 | `FileStored` | `transfer_id`, `version_id`; получатель проверил хеш, атомарно опубликовал файл и зафиксировал версию. |
| 13 | `SyncComplete` | `folder_id`; обмен по папке завершён на текущем снимке. |
| 14 | `Error` | `code`, `message`, опционально `folder_id`, `relative_path`, `transfer_id`; структурированная ошибка. |
| 15 | `SyncStart` | `folder_id`; запрос обмена по уже принятой папке после повторного подключения. |

Коды этой таблицы закреплены в `src/network/frame.h`. Новые типы получают новые коды; существующие коды и значения полей версии 1 не переопределяются. Кодек `src/network/frame.cpp` проверяет границы и тип кадра. Проверка JSON и прав доступа принадлежит уровню сообщений и синхронизатору: успешное декодирование кадра само по себе не означает допустимость сообщения.

### Схемы JSON

Все ключи ниже обязательны, кроме помеченных `?`. UUID — строка в нижнем регистре по форме `xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx` без фигурных скобок. `u64` — десятичная строка без знака и ведущих нулей, кроме `"0"`. Числовые `protocol_version`, `page_number`, `page_count` — неотрицательные JSON integer в указанном диапазоне. Повторяющиеся ключи, неверные типы, невалидный UTF-8 и недопустимые значения отклоняются как `INVALID_MESSAGE`. Для версии 1 неизвестные дополнительные ключи игнорируются.

```text
Hello          {"protocol_version": 1, "device_id": UUID}
HelloAck       {"protocol_version": 1}
FolderInvite   {"folder_id": UUID, "owner_device_id": UUID, "display_name": string}
FolderAccept   {"folder_id": UUID}
FolderReject   {"folder_id": UUID, "reason": string}
SyncStart      {"folder_id": UUID}
IndexPage      {"folder_id": UUID, "page_number": integer,
                "entries": [IndexEntry, ...]}
IndexEnd       {"folder_id": UUID, "page_count": integer}
FileRequest    {"folder_id": UUID, "relative_path": string, "version_id": UUID}
FileBegin      {"transfer_id": UUID, "folder_id": UUID,
                "relative_path": string, "version_id": UUID,
                "size": u64, "sha256": hex64, "vector": VersionVector}
FileEnd        {"transfer_id": UUID}
FileStored     {"transfer_id": UUID, "version_id": UUID}
SyncComplete   {"folder_id": UUID}
Error          {"code": ErrorCode, "message": string,
                "folder_id"?: UUID, "relative_path"?: string,
                "transfer_id"?: UUID}

IndexEntry     {"relative_path": string, "version_id": UUID,
                "size": u64, "sha256": hex64, "vector": VersionVector}
VersionVector  {UUID: u64, ...}
```

Строки ограничены длиной сериализованного JSON-кадра в 64 КиБ; `relative_path` дополнительно ограничен 4096 байтами UTF-8 и проверяется по правилам путей. `display_name` и `reason` — до 256 байт UTF-8. Вектор не содержит нулевых счётчиков и не более двух записей в первой версии. Один `IndexPage` содержит не более 256 записей и обязан укладываться в 64 КиБ; отправитель уменьшает число записей в странице при длинных путях. Пустой индекс передаётся одним `IndexEnd` с `page_count: 0`. Порядок записей — по байтам UTF-8 пути, затем по строке `version_id`; это обеспечивает одинаковые страницы при повторном снимке. Значение `sha256` вычислено по байтам содержимого файла; `version_id` сохраняется при передаче.

Пример запроса (JSON является только нагрузкой кадра типа 8):

```json
{"folder_id":"11111111-1111-4111-8111-111111111111","relative_path":"notes/todo.txt","version_id":"22222222-2222-4222-8222-222222222222"}
```

Для `FileChunk` нагрузка бинарная: 16 байт UUID в порядке RFC 4122, 8 байт `offset` big-endian, затем от 1 до 65 536 байт файла. Нулевой файл передаётся `FileBegin` и `FileEnd` без `FileChunk`. Каждый `transfer_id` уникален в сессии; повторно использованный ID с другими параметрами — `TRANSFER_STATE`.

### Порядок и повторные подключения

После взаимного TLS каждый узел отправляет один `Hello`; затем отвечает одним `HelloAck`. До получения обоих `Hello` и `HelloAck` сообщения о папках отклоняются. Несовместимая версия закрывает сессию. В рамках одной TCP-сессии каждый узел последовательно обрабатывает одну папку, чтобы две передачи не публиковали один путь одновременно.

Для нового `folder_id` владелец отправляет `FolderInvite`; до явного выбора пустого локального каталога получатель не отправляет `FolderAccept`. Владелец сохраняет разрешение на доступ **до** отправки индекса. Для уже принятой папки инициатор отправляет `SyncStart`; другая сторона проверяет доверие и разрешение, после чего обе начинают снимок индекса. Получатель `SyncStart` с чужой папкой отвечает `ACCESS_DENIED` без раскрытия метаданных. Одновременные `SyncStart` той же папки сливаются в один обмен; для ручного соединения инициатор TCP является инициатором `SyncStart`.

Каждая сторона отправляет страницы собственного снимка последовательно и затем `IndexEnd`. Получатель отвергает пропущенный или повторённый `page_number` в рамках снимка. Данные индекса обрабатываются порциями; хранить все страницы в памяти не требуется. Запрашивать файл можно после обоих `IndexEnd`. Запрос и передача могут идти в обе стороны по одному соединению, но для одного `relative_path` допускается одна незавершённая публикация. После `FileStored` отправитель может забыть временное состояние передачи; отсутствие `FileStored` означает, что передача не подтверждена. `SyncComplete` отправляется после завершения всех запрошенных передач или регистрации ошибок конкретных путей; локальный статус сообщает, были ли такие ошибки.

Обрыв TCP завершает сессию и все её `transfer_id`. Неподтверждённые временные файлы сверяются при следующем запуске; после нового `SyncStart` недостающий файл запрашивается целиком. Повторно полученный `version_id`, уже сохранённый с тем же SHA-256, подтверждается без новой копии. Тот же `version_id` с иным SHA-256 отклоняется как `TRANSFER_STATE`. На `Error` для пути узлы продолжают остальные пути; ошибки сессии и доступа закрывают соответствующий обмен.

Индекс одной папки отправляется страницами с последовательными `page_number` от нуля. Размер страницы ограничен размером JSON-кадра, ориентир — не более 256 записей. Источник публикует в индексе только версии, содержимое которых доступно для чтения; состояние недоступной версии остаётся локальной диагностикой. После получения обеих сторон `IndexEnd` синхронизатор решает, какие версии запросить. Получатель принимает только запрошенный `version_id`, проверяет доступ к `folder_id` и нормализованный путь; источник повторно проверяет доступность файла перед передачей. Повторный `FileRequest` или повторная передача уже сохранённого `version_id` не создаёт новую версию. После разрыва незавершённый файл передаётся заново; докачки части файла в этой версии нет.

`FileChunk.offset` должен совпадать со следующим ожидаемым смещением, сумма байт не может превышать заявленный размер. `FileEnd` допустим лишь после получения всех байт. `FileStored` отправляется только после проверки размера и SHA-256, атомарной публикации и записи в индекс. Если целевой файл изменился во время передачи, перед публикацией заново сравниваются версии; новая локальная правка не перезаписывается молча.

## Ошибки

Код является машинно читаемым, `message` — коротким текстом для диагностики. Сетевой текст не показывается пользователю без нормализации и не используется для принятия решения вместо кода.

| Код | Значение | Последствие |
|---|---|---|
| `PROTOCOL_VERSION` | Несовместимая версия в `Hello` | Закрыть сессию. |
| `INVALID_FRAME` | Повреждённый кадр, неизвестный тип или лимит | Закрыть сессию. |
| `INVALID_MESSAGE` | Кадр корректен, но JSON, поля или состояние сообщения неверны | Закрыть сессию; ошибка допустимого сообщения о конкретном пути использует `INVALID_PATH` или `TRANSFER_STATE`. |
| `UNKNOWN_DEVICE` | Устройство не сопряжено или сертификат не совпал | Отклонить до доступа к папкам; TLS может завершиться ещё до отправки `Error`. |
| `ACCESS_DENIED` | Нет доступа к `folder_id` | Не выдавать индекс или содержимое; закрыть обмен по папке. |
| `INVALID_PATH` | Недопустимый или несовместимый относительный путь | Отклонить этот путь и показать причину. |
| `CONTENT_UNAVAILABLE` | Версия в индексе есть, но файл невозможно прочитать | Не объявлять передачу успешной; повторить после исправления. |
| `HASH_MISMATCH` | Размер или SHA-256 полученного файла не совпал | Удалить временный приём, сохранить прежнюю версию, разрешить повтор. |
| `WRITE_FAILED` | Ошибка временной или атомарной записи | Сохранить прежнюю версию, показать путь и разрешить повтор. |
| `TRANSFER_STATE` | Неверный порядок сообщений или смещение блока | Прекратить текущую передачу. |

Разрыв сокета — локальное событие `CONNECTION_LOST`, которое UI показывает отдельно; отправить сетевой `Error` после разрыва уже невозможно. Отказ пользователя от приглашения передаётся `FolderReject`, а не ошибкой протокола. Для всех ошибок локальная диагностика содержит этап и, если применимо, конкретный путь.

## Последовательность первого обмена

```text
До подключения: оба устройства обменялись открытыми сертификатами и сверили отпечатки.
TCP → взаимный TLS → проверка сохранённых сертификатов
Hello ↔ Hello → HelloAck ↔ HelloAck
A: FolderInvite → B: выбор пустой локальной папки → FolderAccept
A ↔ B: IndexPage ... IndexEnd
B: FileRequest → A: FileBegin, FileChunk ..., FileEnd → B: FileStored
A ↔ B: SyncComplete
```

При следующих подключениях приглашение не требуется: инициатор отправляет `SyncStart`, обе стороны используют сохранённую привязку `folder_id` и сравнивают содержимое в обе стороны. Автоматическое UDP-объявление передаёт только `device_id`, версию обнаружения и TCP-порт; IP берётся из адреса отправителя. UDP не меняет доверие, доступ к папке или правила TLS. Для предотвращения одновременных автоподключений инициатором становится устройство с меньшим `device_id`.
